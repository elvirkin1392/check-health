# План: день болезни считается по календарю пользователя

Спецификация: [spec.md](./spec.md)

## Обзор решения

Одна чистая функция отвечает на вопрос «какое сегодня число у этого человека» и возвращает
календарную строку. Все места, где сейчас стоит `dt.now()` в роли дня, берут день у неё.
Арифметика по календарным датам остаётся без пояса — она в нём не нуждается (§9).

Пояс в эти места попадает тем же путём, что уже проложил `lang`: сервисный слой читает его
из документа пользователя и кладёт в `params` шаблона сообщения. Фича 001 уже добавила поле
`timeZone`, чтение `getDbUserTimeZone` и приведение `resolveTimeZone` с запасным UTC —
новых источников данных не требуется.

Слой базы перестаёт знать про «сегодня»: `getDbLastIllDay` принимает день пользователя
аргументом вместо того, чтобы вызывать `dt.now()` у себя. Это же убирает её двойной
возвращаемый тип.

## Данные

Изменений в документах нет. Поле `timeZone` добавлено фичей 001, опциональное, старые
документы читаются. Формат дат — календарная строка без смещения, как есть.

Миграции нет и не будет: уже записанные дни не пересчитываются (FR-9, сценарий 6 спеки).
Записи, сделанные до этой фичи по UTC, у пользователя восточнее могут быть на сутки раньше —
восстановить нельзя, момент нажатия не сохранён.

## Интерфейсы

Команды бота и `callback_data` не меняются — меняются только значения дат внутри них.

Сигнатуры, на которые будут опираться тесты:

- `userToday(timeZone?: string | null): string` — `'YYYY-MM-DD'`, при неизвестном поясе UTC
- `userYesterday(timeZone?: string | null): string`
- `userTodayMonth(timeZone?: string | null): {year: number, month: number}`
- `calcPeriodBetweenDates(start: string, end: string)` — только календарные строки
- `extractPeriodsFromYear(periods, today: string)`
- `getDbLastIllDay(user: User, today: string): Promise<string | undefined>`
- `getMessageTemplate(command, params)` — `params` получает `timeZone`

## Требования → решение

| FR | Решение |
|---|---|
| FR-1 | кнопки «первый день» и «сегодня» берут `userToday(timeZone)` |
| FR-2 | кнопка «со вчера» берёт `userYesterday(timeZone)` |
| FR-3 | гейт календаря сравнивает день с `userToday(timeZone)`, а не с `dt.now()` |
| FR-4 | начальный месяц календаря — `userTodayMonth(timeZone)` |
| FR-5 | сервис передаёт `userToday(timeZone)` в расчёт здоровых дней |
| FR-6 | `extractPeriodsFromYear` отсчитывает год назад от переданного дня |
| FR-7 | `getDbLastIllDay` подставляет переданный день вместо `dt.now()` |
| FR-8 | `userToday` приводит пояс через существующий `resolveTimeZone` → UTC |
| FR-9 | формат хранения не трогаем; `calcPeriodBetweenDates` работает со строками, `setZone` к сохранённым датам не применяется нигде |

## Риски и ограничения

- **Тесты должны управлять «сейчас».** Критерии приёмки говорят про конкретный момент
  (вечер в UTC+5). Берём `Settings.now` из luxon — подменяется в `beforeEach`,
  восстанавливается после. Продакшн-код от этого не меняется, параметр `now` не нужен.
- **`getMessageTemplate` получает ещё одно поле в `params`.** Шаблоны уже принимают `any`,
  поэтому забыть передать `timeZone` компилятор не поймает. Поэтому на каждый FR с датой —
  тест, а не надежда на типы.
- **Пояс читается ещё одним запросом к базе** в `sendResponseToCommand`. Там уже есть запрос
  за языком; при росте нагрузки оба стоит слить в один, сейчас не нужно.
- **Mini App не затронут**, но его статистика продолжит считать по браузеру, а бот — по
  сохранённому поясу. Для одного человека это один и тот же пояс в обычном случае и может
  разойтись, если он задал пояс командой, а смотрит статистику из другого места. Вынесено
  за рамки спеки осознанно.
- **Лимиты Telegram не затрагиваются**: длина `callback_data` не меняется, в неё по-прежнему
  идёт дата вида `2026-10-10`.
- Деплой на Cloud Run не меняется. Биллинг проекта сейчас выключен — проверка будет только
  локальной и в тестах.
