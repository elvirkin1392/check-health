# Конституция проекта check-health

Постоянные правила, которые действуют для каждой фичи. `plan.md` каждой фичи проверяется на соответствие им.
Здесь только то, что (а) не меняется от фичи к фиче, (б) можно проверить, (в) иначе приходилось бы повторять в каждой спеке.
Разовые решения — в `plan.md` фичи, а не здесь.

Версия: 4 · обновлено 2026-10-14

## Процесс

### 1. Спецификация — источник правды

Поведение меняется сначала в `spec.md`, потом в коде. Код без требования в спеке — лишний.
Если в ходе реализации выяснилось новое, спека обновляется, а не остаётся врать.

### 2. Тесты из критериев приёмки, до реализации

Каждый AC покрыт тестом. Тесты пишутся до реализации и во время реализации не меняются
(`.claude/tests.lock`). Тест проверяет поведение из спеки, а не детали реализации.

### 3. Зелёный CI — часть определения «готово»

Сервер: `npm run check-ts`, `npm test`. Клиент: `npm run lint`, `npm run check-ts`, `npm test`.
Фича не считается законченной, пока что-то красное.

## Архитектура

### 4. Границы слоёв соблюдаются

Сложившееся разделение: `*.api` — внешние вызовы, `*.service` — логика, `*.db` — запросы к MongoDB,
`*.controller` / `*.router` — HTTP, `helpers/` — чистые функции.
Чистая логика (расчёт периодов, форматирование, разбор callback_data) живёт в чистых функциях
и тестируется без Telegram и без базы. Моки — только на границах.

### 5. Состояние живёт в базе, а не в памяти процесса

Cloud Run может перезапустить или остановить инстанс в любой момент. Всё, что должно
переживать рестарт (cron-задачи, ожидание ввода от пользователя), пишется в MongoDB
и восстанавливается при старте. Переменные модуля — не хранилище.

### 6. Типизация

Новый код — `.ts` / `.tsx`, новые `.js` файлы не добавляем. На границах (документы базы,
апдейты Telegram, аргументы функций) типы описываются, `any` не оставляем.
Ослаблять настройки `tsconfig.json` нельзя, усиливать — отдельной задачей.

Оставшиеся `.js` файлы переводим в TypeScript по мере затронутости: если фича правит такой файл,
он переименовывается и типизируется в рамках этой же работы. Конвертация упоминается в `plan.md`,
делается отдельным коммитом и не меняет поведение — иначе её не отличить от самой фичи в ревью.
Если файл задет одной строкой, а перевод тянет за собой половину проекта, это допустимо отложить —
но решение фиксируется в `plan.md`, а не замалчивается.

### 7. Простота

Существующий стек: Express, MongoDB, React, luxon, Jest. Новая зависимость — только с обоснованием
в `plan.md` (что именно она решает и почему не хватает текущих). Минимальное изменение, выполняющее спеку.

## Данные и время

### 8. Схема только расширяется

У бота есть реальные пользователи, их документы уже лежат в базе. Новые поля — опциональные,
код читает документы без них. Переименование и удаление полей — отдельная задача с планом миграции
и обратной совместимостью на время раскатки. Деструктивных миграций нет.

### 9. День считается по локальному времени пользователя

Моменты времени хранятся строками ISO с указанием смещения. Величины с точностью до дня
(начало и конец болезни) хранятся календарной датой без времени и без смещения: `2026-10-01`.
Переводить такую дату в другой пояс через `setZone` нельзя: `2026-10-01`, разобранная
в поясе UTC+5 и приведённая к UTC, превращается в `2026-09-30` — ровно та ошибка на сутки,
от которой смещение должно было защищать. Вся арифметика — через luxon.

Границы дня (начало и конец болезни, «сегодня», напоминания, статистика за период)
считаются в часовом поясе пользователя, а не сервера. `dt.now()` без `setZone` в такой логике —
ошибка: на Cloud Run это UTC, и у пользователя в UTC+5 вечерняя запись уедет на вчера.
Пояс нужен там, где участвует «сейчас». Арифметика по уже сохранённым календарным датам
от пояса не зависит и в нём не нуждается — длительность периода `2026-10-01`…`2026-10-09`
одинакова в любом поясе, и смена пояса сохранённые даты не сдвигает.

Часовой пояс пользователя хранится в его документе — опциональное поле `timeZone`
с IANA-именем. Он приходит из Mini App (`Intl.DateTimeFormat().resolvedOptions().timeZone`)
или задаётся командой бота; выбор, сделанный человеком, автоматика не перетирает.
Если пояс неизвестен — фича должна сказать в спеке, что делает: спрашивает пользователя
или берёт оговорённое значение по умолчанию. Значение по умолчанию сейчас — UTC.

## Надёжность

### 10. Бот не молчит

Ошибка в одном сообщении, записи или cron-задаче не ломает обработку остальных
(webhook, восстановление задач при старте). Ошибка логируется с контекстом, пользователь получает ответ.
Повторная доставка апдейта от Telegram не должна создавать дубль записи.

### 11. Ограничения Telegram API соблюдаются явно

`callback_data` ≤ 64 байт, лимиты длины сообщений и размера клавиатуры. Ответ Telegram проверяется:
отказ API — это ошибка, а не тишина. На каждое такое ограничение — тест.

### 12. Все тексты для пользователя — через i18n

Никаких строк в коде: ключи в `telegramBot/i18n`, переводы `en` и `ru` добавляются вместе.
Непереведённый ключ — незакрытая задача.

## Безопасность и приватность

### 13. Входящее не доверяем

`initData` Mini App проверяется по подписи, webhook Telegram — по secret token.
Эндпоинты закрыты JWT по умолчанию; публичный эндпоинт — осознанное решение с пометкой в `plan.md`.
Пользователь видит и меняет только свои данные.

### 14. Медицинские данные не утекают в логи

`ill_periods`, `woman_days`, `blood_tests`, `bio` — чувствительные данные о здоровье.
В логи попадают идентификаторы и коды ошибок, а не содержимое записей, тексты сообщений,
токены и `initData`. Секреты только через переменные окружения — не в коде, не в спеках, не в тестах.

## Как менять эту конституцию

Принцип добавляется, когда одно и то же замечание возникло дважды. Принцип удаляется, если
за ним не следят — мёртвое правило хуже отсутствующего. Изменение конституции — отдельный коммит
с причиной; версия и дата в начале файла обновляются.
