# План: загрузка файла с результатами анализов

Спецификация: [spec.md](./spec.md)

## Обзор решения

Человек присылает боту PDF. Бот сразу отвечает «принял» и кладёт **черновик разбора**
в MongoDB; разбор идёт после ответа Telegram, его результат дописывается в тот же черновик.
Когда разбор закончен, бот присылает список найденных показателей с кнопками
«Подтвердить / Исправить / Отменить». В документ пользователя попадает только
подтверждённое — до этого все данные живут в черновике.

Три решения определяют всё остальное:

1. **Черновик — отдельная коллекция `lab_imports`, а не поле в документе пользователя.**
   Черновик недолговечен, его содержимое — медицинские данные до подтверждения,
   и у него есть состояние (принят → разобран → ждёт даты → ждёт правки → сохранён).
   По §5 это состояние обязано пережить рестарт Cloud Run, а по §8 раздувать
   документ пользователя транзиентными записями не нужно. Коллекция со своим TTL
   чистится сама.

2. **Ответ Telegram отправляется до разбора.** Сейчас `/api/listenWebHook`
   дожидается `manageTgUpdates` целиком. Разбор PDF — это секунды, Telegram за это
   время переотправит апдейт, и по §10 появится дубль. Поэтому обработчик документа
   делится надвое: быстрая часть (проверить тип и размер, записать черновик, ответить)
   и медленная (скачать, разобрать, отправить результат).

3. **Справочник показателей — свой, а не LOINC.** Обоснование ниже, как требует спека.

## Почему не LOINC

Спека велела проверить готовый справочник. Проверила:

| Что смотрела | Что оказалось |
|---|---|
| Полный LOINC | ~90 тысяч кодов. Распространяется бесплатно, но под лицензией с регистрацией. Для двух-трёх десятков показателей, которые приложение показывает, это несопоставимый объём |
| LOINC Top 2000+ Lab Observations | CSV с номером LOINC, длинным и коротким названием, классом и рангом. **Только по-английски.** Ранжирование заморожено до обновления частотных данных |
| LOINC Russian, Russia Edition | Отдельный языковой вариант (версия 2.77, Ярославская медакадемия, февраль 2024), распространяется отдельно через LOINC/UMLS |

Главное, чего нет ни в одном из файлов: **русских синонимов, под которыми показатель
печатают в бланке.** LOINC даёт каноническое длинное имя
(`Bilirubin.total [Mass/volume] in Serum or Plasma`), а лаборатория пишет
«Билирубин общий». Сопоставлять строку из бланка всё равно пришлось бы по своему
списку синонимов — то есть готовый справочник не снимает основную работу,
а добавляет к ней лицензию, загрузку с регистрацией и 90 тысяч строк в репозитории.

**Решение (§7):** свой справочник в `shared/analytes.tsx` — продолжение того,
что уже начато в 003 (`vitamin_d`, `bilirubin`, `creatinine`). Каждая запись:
свой код, подписи `en`/`ru`, список синонимов для сопоставления и **опциональное
поле `loinc`**. Поле пустое сейчас и заполняется по мере надобности — это цена
одной строки на показатель и единственное, что понадобится, если однажды данные
придётся отдавать наружу в стандарте.

## Какие PDF считаются поддерживаемыми

Спека требует сказать это прямо. Фича работает на PDF, у которых есть **текстовый слой**
и в которых показатель занимает одну строку с полями в постоянном порядке:
название — значение — единица — границы нормы (последние два могут отсутствовать).

Не поддерживается:

- **Сканы и фотографии, вложенные в PDF** — текста не извлекается вовсе. Определяется
  тем же способом, которым разбирается всё остальное: из файла не вышло ни одной
  текстовой строки → сценарий 4. Отдельного распознавания изображений нет (решение спеки).
- **Вёрстка в несколько колонок или с переносом строки внутри показателя** — строка
  не сложится в нужную форму и уйдёт в список нераспознанного (сценарий 5).

Набор поддерживаемых вёрсток задаётся **фикстурами**: на каждую вёрстку —
PDF в `server/telegramBot/labImport/fixtures/` и правило разбора строки. Расширение
набора — это новая фикстура плюс правило, без переделки остального. Первая фикстура
собирается в фазе тестов искусственно (сгенерированный PDF с типовой таблицей),
потому что настоящих бланков в репозитории быть не должно (§14).

## Данные

### Документ пользователя

`blood_tests` уже существует и всегда пустой — тип заполняется впервые, миграция
не нужна, старые документы читаются как есть (§8).

```
AnalyteResult = {
  code?: string          // наш код, если показатель узнан; иначе поля нет
  name: string           // как записано в файле — показывается, когда кода нет
  value: string          // строка, а не число: «отрицательно», «следы», «<0.5»
  unit?: string
  normal?: {from?: number, to?: number, raw?: string}
  date: string           // календарная дата YYYY-MM-DD, без времени и смещения (§9)
}
```

`value` — строка намеренно. Граничный случай спеки требует не терять строку
с нечисловым результатом, а такие в бланках обычны.

### Черновик разбора — коллекция `lab_imports`

```
LabImportDoc = {
  draftId: string        // 8 hex-символов: короткий, чтобы влезть в callback_data (§11)
  userId: number         // Telegram id
  fileUniqueId: string   // от Telegram, стабилен для одного файла
  status: 'received' | 'parsed' | 'awaiting_date' | 'awaiting_edit' | 'done' | 'failed'
  createdAt: string      // ISO со смещением (§9)
  rows?: AnalyteResult[] // распознанное
  unparsed?: string[]    // нераспознанные и конфликтующие строки (FR-10)
  date?: string          // календарная дата анализа
  editingRow?: number    // какую строку человек правит
  failureCode?: string   // код причины, не текст ошибки (§14)
}
```

Уникальный индекс по `{userId, fileUniqueId}` среди незавершённых черновиков —
переотправленный Telegram апдейт не создаёт второй черновик (§10).
TTL-индекс по `createdAt` — черновики с медицинскими данными не лежат вечно (§14).

### Зависшие черновики

Рестарт во время разбора оставляет черновик в `received`. При старте проходом
рядом с `restoreJobs` такие черновики помечаются `failed` с кодом `interrupted`,
и человек получает сообщение «разбор не завершился, пришлите файл снова».
Повторно скачивать файл не пытаемся: ссылка Telegram на файл живёт недолго,
а своей копии у нас по решению спеки нет.

## Интерфейсы

### Бот

| Что | Как |
|---|---|
| Сообщение с документом | не команда, обрабатывается по наличию `message.document` |
| `callback_data` подтверждения | `{"command":"lab_ok","value":"a1b2c3d4"}` — 39 байт |
| `callback_data` отмены | `{"command":"lab_no","value":"a1b2c3d4"}` — 39 байт |
| `callback_data` правки | `{"command":"lab_fix","value":{"d":"a1b2c3d4","r":12}}` — 53 байта |
| `callback_data` даты | `{"command":"lab_date","value":"2026-10-21"}` — 43 байта. Вариант с черновиком внутри кнопки занял бы ровно 64 — см. ниже |

Про последнюю стоит сказать отдельно. Очевидный вариант — положить в кнопку
и черновик, и дату — даёт `{"command":"lab_date","value":{"d":"a1b2c3d4","v":"2026-10-21"}}`,
то есть **ровно 64 байта: предел §11 без единого байта запаса**. Удлинись `draftId`
на символ — и кнопка молча перестанет работать.

Поэтому черновик в кнопке не передаётся: календарь возвращает только дату,
а какой черновик её ждёт, берётся из `lab_imports` по `userId` и статусу
`awaiting_date`. Состояние и так в базе (§5) — дублировать его в кнопке незачем,
а 21 байт запаса дороже симметрии с остальными кнопками. На длину каждой
кнопки — тест (§11).

### Правка значения (FR-6)

Инлайн-клавиатурой число не введёшь. Поток: кнопка «Исправить» → бот пишет
«пришлите строку в виде `номер = значение`» и ставит черновику `awaiting_edit`
→ человек отправляет `3 = 12.5` обычным сообщением → бот правит строку черновика
и присылает список заново. Непонятный формат — ответ с примером, черновик
остаётся в том же статусе.

Отсюда следует: `manageTgUpdates` должен начать обрабатывать ветку `message`,
которую сейчас игнорирует. Текстовое сообщение без ждущего черновика
по-прежнему остаётся без ответа — это не регресс, но и не повод молчать:
отвечаем подсказкой `/start`.

### Чистые функции (на них и пишутся тесты)

```
parsePdfText(text: string): {rows: ParsedRow[], unparsed: string[]}
matchAnalyte(name: string): {code?: string}
extractDate(text: string): string | undefined
mergeResults(saved: AnalyteResult[], incoming: AnalyteResult[]): AnalyteResult[]
applyEdit(rows, command: string): {rows} | {error: 'format'}
isAcceptableDate(date: string, today: string): boolean
```

Разбор, сопоставление и дедупликация не знают ни про Telegram, ни про базу (§4).
Скачивание файла и запись черновика — единственные места с моками.

## Требования → решение

| FR | Решение |
|---|---|
| FR-1 | Ветка `document` в `manageTgUpdates`. Проверка: `mime_type === 'application/pdf'` и `file_size ≤ 5 МБ` (бланк анализов меньше; лимит Telegram на `getFile` — 20 МБ). Непрошедшее — отказ до скачивания |
| FR-2 | `parsePdfText` по строкам текстового слоя: название, значение, единица, границы нормы. Текст извлекается `pdfjs-dist` с координатами, строки собираются по `y` |
| FR-3 | `extractDate` ищет дату в тексте. Не нашла — черновик в `awaiting_date`, человеку та же календарная клавиатура, что в `cold_start`, с целью `l`. Календарь уже запрещает будущие дни; `isAcceptableDate` дополнительно отсекает дату старше 10 лет |
| FR-4 | `matchAnalyte` сопоставляет название с синонимами справочника: регистр и лишние пробелы не важны. Нашлось — пишется `code` и `name` из файла; не нашлось — только `name` |
| FR-5 | Черновик живёт в `lab_imports`. В `users.blood_tests` запись идёт **только** по кнопке `lab_ok` |
| FR-6 | Поток `awaiting_edit`, описан выше |
| FR-7 | `Table.tsx` переходит с `mock.tsx` на `blood_tests` из `/api/profile`. Предыдущее значение показателя — последняя более ранняя запись **с той же единицей**: сравнивать мг/дл с мкмоль/л нельзя (граничный случай спеки). Единицы не совпали — в колонке «пред.» прочерк |
| FR-8 | `mergeResults` отбрасывает строки, у которых совпали дата и ключ показателя (`code` если есть, иначе приведённое `name`) |
| FR-9 | Ни одной распознанной строки — черновик `failed`, человеку причина, `users` не меняется |
| FR-10 | `unparsed` показывается отдельным блоком после списка распознанного. Туда же попадает второе вхождение того же показателя в одном файле с другим значением: молча выбирать из двух значений нельзя |
| FR-11 | В логи идут `userId`, `draftId`, количество строк и код причины. Ни названий, ни значений, ни имени файла (в имени бывает фамилия). Ошибка библиотеки логируется как `error.name` и свой код — текст исключения может содержать фрагмент файла |
| FR-12 | Ключи в `telegramBot/i18n/dictionaries/{en,ru}.tsx`, оба языка одним коммитом (§12) |

## Новая зависимость

`pdfjs-dist` — PDF.js от Mozilla. Обоснование по §7:

- Текущего стека не хватает принципиально: PDF — бинарный формат со сжатием,
  руками его не читают.
- Почему не `pdf-parse`: он склеивает весь текст в одну строку и на таблицах
  даёт перемешанный порядок — именно то, что здесь разбирать.
  `pdfjs-dist` отдаёт текстовые фрагменты с координатами, по которым строка таблицы
  собирается обратно.
- Почему не отправлять файл в LLM на разбор: медицинский документ ушёл бы третьей
  стороне (§14), результат невоспроизводим, и на такой разбор нельзя написать тест.
- OCR не берём: решение спеки — только PDF с текстом.

## Риски и ограничения

- **Разбор чужой вёрстки — догадка.** Поэтому в спеке и есть сценарий 2:
  подтверждение обязательно. План не обещает процента распознавания — обещает,
  что нераспознанное видно (FR-10), а неподтверждённое не сохраняется (FR-5).
- **`callback_data` даты была на пределе 64 байт** — решено тем, что черновик
  берётся из базы, а не из кнопки. На каждую кнопку фичи — тест длины (§11).
- **Вебхук перестаёт ждать обработку.** Побочный эффект: ошибка в разборе больше
  не превратится в 500 для Telegram. По §10 это и правильно (апдейт обработан,
  переотправлять нечего), но ошибку надо логировать явно, иначе она исчезнет.
- **Рестарт в середине разбора** теряет работу: файла у нас нет. Человеку
  говорим прямо и просим прислать снова.
- **Разбор нагружает инстанс.** Cloud Run считает CPU; большой PDF от одного
  человека задержит ответы остальным. Лимит 5 МБ и отказ до скачивания —
  первая защита; очередь и отдельный воркер в эту фичу не входят.
- **Таблица клиента красит нечисловое значение в «плохо»:** `Number('отрицательно')`
  даёт `NaN`, сравнение ложно, и строка получает класс `bad`. Сейчас это не видно,
  потому что данные выдуманные. С настоящими — видно сразу, и починить надо
  в этой же фиче, иначе FR-7 выполнен формально.
- **TTL на черновиках удалит и те, что человек не успел подтвердить.** Срок берём
  с запасом (7 дней) и пишем в сообщении, что разбор ждёт подтверждения.
