# План: переводы в Mini App

Спецификация: [spec.md](./spec.md)

## Обзор решения

Клиент получает свой словарь и свою функцию перевода, устроенные так же, как у бота.
Общим остаётся только то, о чём обе половины обязаны договориться: список языков
и приведение значения к допустимому — они уже лежат в `shared/lang.tsx` и используются
ботом. Проверено сборкой: клиент импортирует оттуда без правки конфигурации Vite.

`translate` выносится в `shared/` вместе со списком языков. Подстановка `{{name}}` — это
договор между теми, кто пишет словари, и тем, кто их отрисовывает: две копии дадут два шанса
разойтись, и один и тот же ключ с одним и тем же параметром отрисуется по-разному в боте
и в приложении.

Вынос попутно чинит бота. Сейчас его `translate` на отсутствующем ключе возвращает
`undefined` без параметров и **бросает исключение** с параметрами — то есть непереведённый
ключ способен уронить обработку сообщения, что прямо противоречит §10. FR-7 клиента требует
обратного поведения, и реализованное один раз в общем коде оно достаётся обеим половинам.

Язык определяется тем же правилом, что в боте: сохранённый выбор → `language_code`
Telegram → английский. Считает его **сервер**, а не клиент: у сервера есть и сохранённое
значение, и проверенный подписью `initData`, тогда как клиентский `initDataUnsafe`
подписью не проверен (§13). Клиент получает готовый язык в ответе на вход и держит его
рядом с токеном, как уже делает с именем пользователя.

Переключатель языка пишет выбор на сервер. Эндпоинт профиля сейчас только читает —
появляется запись.

## Данные

Новых полей нет. Язык уже хранится в документе пользователя (`lang`), его пишет бот.
Mini App пишет туда же — отсюда FR-4 без всякой синхронизации: поле одно, последняя
запись и есть последний выбор.

Коды показателей (FR-9) в документе пользователя не появляются: `blood_tests` пустой
и этой фичей не заполняется. Коды появляются только в моковых данных, которыми живёт
страница анализов. Настоящее хранение определит фича [004](../004-lab-file-import/spec.md).

## Интерфейсы

- Ответ на вход через Telegram дополняется полем с языком, вычисленным на сервере.
- Эндпоинт профиля получает операцию записи языка; закрыт JWT, меняет только свой документ (§13).
- `translate(key, lang, params?)` — одна функция в общем коде, привязываемая к своему
  словарю каждой половиной. Типизация ключей сохраняется: опечатка остаётся ошибкой компиляции.
- Справочник показателей: соответствие кода и подписи на двух языках.

## Требования → решение

| FR | Решение |
|---|---|
| FR-1 | строки из разметки переезжают в словарь; в компонентах остаются только ключи |
| FR-2 | `client/src/i18n/dictionaries/en.tsx` и `ru.tsx`, оба пополняются вместе |
| FR-3 | `SUPPORTED_LANGUAGES` и `resolveLang` импортируются из `shared/lang.tsx` |
| FR-4 | и бот, и клиент пишут одно поле `lang` |
| FR-5 | правило считает сервер: сохранённое → `language_code` из проверенного `initData` → `en` |
| FR-6 | формат даты берёт язык интерфейса вместо жёсткого `en-US` |
| FR-7 | общий `translate` при отсутствии ключа возвращает сам ключ — ни страница, ни обработка сообщения не падают |
| FR-8 | переключатель пишет выбор на сервер; при загрузке язык берётся из сохранённого, а не вычисляется |
| FR-9 | подпись показателя берётся из справочника по коду |
| FR-10 | показателя нет в справочнике — выводится записанное значение |

## Риски и ограничения

- **`initDataUnsafe` подписью не проверен.** Поэтому язык считает сервер, а не клиент.
  Если план реализации соблазнится прочитать `language_code` прямо в браузере — это нарушение §13.
- **Первый экран до входа.** `PageAuth` рисуется раньше, чем сервер что-либо ответил.
  Язык там берётся из сохранённого в прошлый раз, иначе английский. Переключать язык
  до входа возможности нет, и это нормально.
- **Открытая вкладка не меняет язык**, если его переключили в боте: обновится при перезагрузке.
  Записано в граничных случаях спеки.
- **Русский длиннее английского.** Подписи кнопок и столбец названий показателей шире;
  вёрстку надо проверить на узком экране, а не только в десктопе.
- **Вынос `translate` меняет поведение бота** на отсутствующем ключе: было `undefined`
  или исключение, станет сам ключ. Это улучшение и согласуется с §10, но изменение
  поведения, а не чистая перестановка кода — отмечено здесь, а не замолчано.
- **У клиента нет ни одного теста** (`jest --passWithNoTests`). Фаза тестов заводит их
  с нуля, а не дополняет существующие.
- **Vite в режиме разработки** ограничивает доступ к файлам вне своего корня. Сборка
  с импортом из `shared/` проверена и проходит; `npm run dev:client` нужно проверить
  отдельно — при необходимости расширить `server.fs.allow`.
- Деплой не меняется. Биллинг GCP выключен, но клиент уезжает на GitHub Pages
  и от этого не зависит.

## Проверка конституции

| Принцип | Соблюдён? | Комментарий |
|---|---|---|
| 1. Спека — источник правды | да | спека согласована, открытых вопросов нет |
| 2. Тесты из критериев приёмки | да | фаза тестов до реализации; у клиента тесты появляются впервые |
| 3. Зелёный CI | требование | сервер и клиент: `check-ts`, `test`, `lint`, `build` |
| 4. Границы слоёв | да | словари и `translate` — чистые функции; запись языка в `*.db`, HTTP в `*.controller` |
| 5. Состояние в базе | да | выбор языка переживает перезапуск, потому что лежит в документе пользователя |
| 6. Типизация | да | ключи словаря типизированы, как у бота: непереведённый ключ — ошибка компиляции |
| 7. Простота | да | новых зависимостей не предполагается; `translate` переиспользуется вместо второй копии |
| 8. Схема расширяется | н/п | новых полей нет, `lang` уже существует |
| 9. День по времени пользователя | н/п | даты только форматируются, границы дня не считаются |
| 10. Бот не молчит | н/п | путей бота фича не трогает |
| 11. Лимиты Telegram | н/п | `callback_data` не затрагивается |
| 12. Тексты через i18n | да | это и есть цель фичи |
| 13. Входящее не доверяем | да | язык считает сервер по проверенному `initData`; запись закрыта JWT |
| 14. Медданные не в логах | да | новых логов нет; названия показателей — справочник, а не данные пользователя |
