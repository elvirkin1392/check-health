# План: ежедневное напоминание в часовом поясе пользователя

Спецификация: [spec.md](./spec.md)

## Обзор решения

Чистая функция считает расписание напоминания: ежедневный cron-шаблон плюс пояс,
приведённый к валидному (невалидный и отсутствующий → UTC). Все три места, где
расписание нужно — создание задачи, восстановление при старте, перенос при смене
пояса — берут его из этой функции, поэтому «актуальное расписание» определено
в одном месте и проверяется тестами без Telegram и без базы.

Пояс попадает в документ пользователя двумя путями: из Mini App при входе и командой
бота. Из Telegram-апдейта пояс взять нельзя — `message.date` это epoch без смещения,
а в `from` есть только `language_code`.

Устаревшие записи не миграция, а самолечение: при старте расписание записи сравнивается
с актуальным, и при расхождении запись перезаписывается. То же сравнение переиспользуется
при смене пояса.

## Данные

Документ пользователя получает опциональное поле часового пояса (IANA-имя). По принципу 8
поле необязательное: документы без него читаются, код трактует отсутствие как «пояс
неизвестен» и считает по UTC. Переименований и удалений нет.

Запись задачи напоминания получает поле пояса рядом с уже существующим полем расписания.
Старые записи без этих полей остаются валидными и исправляются при первом старте процесса:
ручная миграция не нужна, деструктивных операций нет. Исправление пишется в лог
идентификатором записи и расписанием — без содержимого сообщений (§14).

Отдельно: тип документа задачи описан явно, потому что типизация коллекции — это граница
базы (§6).

## Интерфейсы

- Новая команда бота для смены пояса; её `callback_data` — `{command, value}` с IANA-именем
  пояса, под лимитом 64 байта (§11, покрыто тестом).
- Эндпоинт входа через Telegram Web App принимает дополнительное необязательное поле
  с часовым поясом.
- `getResponseToInlineButton` получает четвёртым аргументом пояс пользователя и может
  вернуть признак «перенести запущенные задачи».
- Cron-слой: задача создаётся с поясом; добавлена операция переноса задач пользователя.

## Требования → решение

| FR | Решение |
|---|---|
| FR-1, FR-2 | ежедневный cron-шаблон на 12:00 + пояс передаются в планировщик |
| FR-3 | опциональное поле в документе пользователя, чтение отдельным запросом |
| FR-4 | шаблон сообщения с клавиатурой; метка кнопки — город и текущее смещение |
| FR-5 | Mini App читает пояс устройства и отправляет при входе |
| FR-6 | проверка имени пояса через luxon до сохранения, на обоих путях |
| FR-7 | приведение пояса к валидному возвращает UTC для неизвестного |
| FR-8 | перенос задач пользователя сразу после сохранения пояса |
| FR-9 | сравнение расписания записи с актуальным при старте и перезапись |
| FR-10 | ключи добавлены в en и ru одновременно |

## Риски и ограничения

- Список поясов фиксирован; человек из пояса вне списка остаётся на UTC, пока не откроет
  Mini App. Вынесено в открытые вопросы спеки.
- Mini App передаёт пояс только при входе, а вход происходит один раз — переезд
  подхватится командой, но не сам. Тоже открытый вопрос.
- Восстановление при старте читает пояс отдельным запросом на каждую задачу. При текущем
  числе пользователей это незаметно; при росте — читать пояса одним запросом.
- Перенос задач опирается на карту хендлеров в памяти процесса. База остаётся источником
  правды, карта лишь позволяет не ждать рестарта; после рестарта она восстанавливается
  из базы.
- Меню команд бота в коде не регистрируется — новую команду нужно добавить в BotFather.

## Проверка конституции

| Принцип | Соблюдён? | Комментарий |
|---|---|---|
| 1. Спека — источник правды | частично | спека написана после кода: работа начиналась как фикс одной строки и выросла в фичу |
| 2. Тесты из критериев приёмки | частично | 29 тестов покрывают AC-1…AC-13, но написаны вместе с кодом, а не до него |
| 3. Зелёный CI | да | `npm run check-ts` и `npm test` зелёные (52 теста); клиентские проверки не запускались — в worktree нет `client/node_modules`, в затронутом файле ошибок нет |
| 4. Границы слоёв | да | расписание и разбор пояса — чистые функции, тестируются без Telegram и базы; запросы к базе в `*.db`, внешний вызов в `*.api` |
| 5. Состояние в базе | да | расписание и пояс задачи в MongoDB, восстанавливаются при старте; карта хендлеров — кеш, не хранилище |
| 6. Типизация | да, с отложенным долгом | `telegram.db.js` переведён в TS отдельным коммитом; остальные серверные `.js` отложены в [000-js-to-ts](../000-js-to-ts/spec.md) |
| 7. Простота | да | новых зависимостей нет: `cron` уже умеет `timeZone`, проверка имени пояса — luxon |
| 8. Схема расширяется | да | новые поля опциональные, старые документы читаются, миграции нет |
| 9. День по времени пользователя | частично | напоминание — да; даты болезни, «сегодня»/«вчера» и статистика остались на UTC, см. «Не входит в фичу» |
| 10. Бот не молчит | да | ошибка на одной записи не ломает остальные при старте и при переносе; каждая логируется с идентификатором |
| 11. Лимиты Telegram | да | `callback_data` кнопок пояса под 64 байта, покрыто тестом |
| 12. Тексты через i18n | да | три новых ключа в en и ru |
| 13. Входящее не доверяем | да | пояс из Mini App проверяется через luxon до записи |
| 14. Медданные не в логах | да | в логах только идентификаторы записей, расписание и пояс |
