Аргументы: $ARGUMENTS

1. Определи папку фичи: из аргументов, иначе — последняя по номеру в specs/.
2. Прочитай specs/constitution.md и spec.md. Если в spec.md остались `[NEEDS CLARIFICATION]` —
   остановись, перечисли их и попроси ответы. План по неясной спеке не строим.
3. Изучи код, который придётся менять: telegramBot/, routes/, cron/, db/, client/src/.
4. Создай plan.md по specs/_templates/plan.md:
   - какие модули/файлы меняются и почему; изменения данных в MongoDB; новые/изменённые эндпоинты и команды бота;
   - как каждый FR реализуется (таблица FR → решение);
   - риски и ограничения (лимиты Telegram API, i18n en/ru, cron, деплой на Cloud Run);
   - проверка конституции: пройдись по каждому принципу, отметь соблюдён / нарушен с обоснованием.
5. Создай tasks.md по specs/_templates/tasks.md:
   - Фаза «Тесты»: задачи на тесты из каждого AC (T001…); в каждой — какой AC покрывает.
   - Фаза «Реализация»: маленькие задачи, каждая проверяема; пометка [P] для независимых; ссылки на FR.
   - Фаза «Проверка»: check-ts, тесты, lint клиента, ручная проверка в боте/Mini App.
6. Если план требует отступить от спеки — не меняй спеку молча, спроси.

В конце: краткое резюме плана, спорные решения и число задач. Код не пиши.
